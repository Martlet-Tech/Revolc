# 拖拽分裂 / 合并窗口 —— 外部参考调研

> **已实施（2026-11-26，commit `34c5007`）**：本文是实施前的外部参考调研；
> 实际方案见 `docs/交接文档.md`「M3 第二阶段」一节和 `src/ui/drag_detach.rs`。
> 主要差异：调研里 Chromium 的磁吸是 15px（`kVerticalDetachMagnetism`），实际采用
> 分离带上下各扩半个标题栏高 = 17px；调研里的 `Target::{Same,New,Existing,None}` /
> `Attached`/`Detached` 状态机未采纳，实际用 `in_band` / `band_owner` / `float_origin`
> 三个纯几何函数 + `WM_COPYDATA` 目标通知。

> 目的：M3.3 要把“把标签拖出条带变成新窗口、拖进别的窗口变回标签”做出来。
> 本文只记录**别人怎么做**以及**哪些能抄、哪些抄不到**，不含本项目的实现细节。
> 调研日期：2026-11-19。

## 结论摘要

1. 这套交互在 Chromium 里有完整实现，且它的落点枚举与我们要的四条路径**一一对应**。
2. Chromium 的状态机有 7 个状态，其中 **4 个是在给平台的 move loop 打补丁**；改用拖影（ghost）后这些状态全部消失。
3. 阈值有实测值：`kVerticalDetachMagnetism = 15px`（触摸 50px），不是“半个条带高”。
4. 手感难点不在“拖出去”，而在**提交那一刻的状态迁移**（谁持有标签、谁负责销毁窗口）。
5. 所有参考实现都是“标签在同一个应用的多个窗口间搬家”；**被搬的是一个已被 `SetParent` 的 Explorer 子窗口**这件事，没有任何开源参考——那部分必须自己写。

## 1. Chromium：唯一完整的参考

文件：

- `chrome/browser/ui/views/tabs/dragging/tab_drag_controller.h` ← 先读这个，枚举和成员名本身就是文档
- `chrome/browser/ui/views/tabs/dragging/tab_drag_controller.cc`
- 旧版（更好读）`chrome/browser/cocoa/tab_view.mm` ← macOS 实现，逻辑几乎是伪代码

### 1.1 落点枚举 —— 与需求一一对应

```cpp
enum TabDraggingDestination {
  kSameWindow = 0,      // 放回原窗口
  kNewWindow = 1,       // 新建窗口
  kExistingWindow = 2,  // 塞进别的窗口
  kAbandoned = 3,       // 丢到桌面 / 放弃
};
```

结论：三条落点不是三套逻辑，而是一个 `drop(dest)` 的四个分支。**不应该按“创建窗口”和“合并窗口”分批实现**，那样插入逻辑要写两遍。

### 1.2 状态机 —— 7 个状态，4 个是平台补丁

```cpp
enum class DragState {
  kNotStarted,             // 还没到拖拽阈值
  kDraggingTabs,           // 在条带内拖
  kDraggingWindow,         // 已脱离，拖的是一个窗口
  kDraggingUsingSystemDnD, // 平台不支持 move loop，退回普通 DnD + 拖拽图标
  kWaitingToExitRunLoop,   // 嵌套 move loop 未退出
  kWaitingToDragTabs,      // 同上（另一种 can_release_capture 情况）
  kWaitingForWindowToShow, // 等新窗口首帧
  kStopped,
};
```

`kWaiting*` 三个状态存在的唯一原因：Windows 上 Chromium 的“标签跟手”是这么实现的——

1. 创建真窗口；
2. `ReleaseCapture()`；
3. 把 `WM_NCLBUTTONDOWN / HTCAPTION` 交给 user32，**由系统接管**拖窗口（`RunMoveLoop`）。

模态循环期间应用收不到鼠标消息，只能在退出后继续，所以必须用状态记住“出来后接到哪个条带”。

**Wayland 上做不到这一点**，Chromium 就退回到 `kDraggingUsingSystemDnD`：普通拖放会话 + 一个标签快照当拖拽图标，新窗口在松手时才建。见 Igalia 的博客（链接见文末）。

对 Revolc 的意义：**走拖影就是走 Chromium 的退路，而这条退路上的状态机只有 3 个状态。**

### 1.3 阈值

- `kVerticalDetachMagnetism`（Chrome 1.0 起、至今仍是这个值）：**15px**，条带上下对称。
- `kTouchVerticalDetachMagnetism`：**50px**（触摸）。
- 名字里的 “magnetism”（磁吸）说明它是**边界加回吸**，不是硬开关：靠近时标签被吸回槽位，越过才脱离。这就是显式写迟滞（进 0.5h / 出 0.3h）的同一个东西。

### 1.4 目标窗口怎么找（macOS 版最清楚）

`tab_view.mm` 里的 `dropTargetsForController` + 鼠标移动分支：

1. 按 **z 序**枚举候选窗口；
2. 光标在窗口矩形内 → 先把该窗口 `orderFront`（提到前面，方便继续拖进去）；
3. 光标再落在它的**条带矩形**内 → 才成为 `newTarget`；
4. 换目标时：旧目标移除占位、记录 `dwellDate`（防抖）。

源条带留一个 **placeholder** 撑住视觉空位——标签被拖走时槽位不塌。

## 2. Qt-Advanced-Docking-System：最接近我们要做的事

仓库：`githubuser0xFFFF/Qt-Advanced-Docking-System`（C++）
关键文件：`src/SectionTitleWidget.cpp`（约 289 行，整个拖拽都在这里）、`src/FloatingWidget.cpp`

它把两种实现都做了，用配置开关切换：

| 模式 | 做法 | 后果 |
|---|---|---|
| `OpaqueUndocking`（默认） | 立即脱离，真建浮动窗口，拖的是窗口本身 | 手感直接，但**无法用 ESC 取消** |
| `DefaultNonOpaqueConfig` | 先建“拖影”，松手才真正停靠 | 可取消、可预览落点 |

非透明模式还提供 `DragPreviewShowsContentPixmap`（拖影画内容快照）、`DragPreviewHasWindowFrame`（拖影像不像窗口）等旗标。

**"真建窗"与"拖影"是同一个功能的两种实现，且工业级库两种都写过** —— 这是 M3.3 选拖影的最强旁证。

## 3. Windows Terminal：Win32 上的产品级做法

仓库：`microsoft/terminal`（C++/WinUI）
关键位置：`src/cascadia/TerminalApp/TabManagement.cpp`、`TerminalPage` 的 drag 收尾、`doc/specs/#5000 - Process Model 2.0/`

核心思路与 Chromium 不同：**搬引用，不搬数据**。

- 拖放载荷里放的是一棵“分屏树”，叶子节点是内容进程的 GUID；
- 目标窗口据此重建结构，再按 GUID 连回内容进程；
- 终端 buffer 从不跨进程移动，变的只是“哪个窗口在渲染这个 swapchain”。

另外两条产品级约束值得记：

- 从最大化窗口撕出的标签，新窗口也要最大化；
- 拖到所有条带范围之外 → 用拖放数据初始化一个新窗口。

对我们的启发只有一半：tab 的“内容”是真实的 Explorer 子窗口，不是可以重新连接的 GUID，所以**必须真的搬 HWND**。

## 5. 对 Revolc 的映射

| Chromium | Revolc | 说明 |
|---|---|---|
| `kNotStarted` | 无状态 | 现有的 `TabPress` 阈值逻辑 |
| `kDraggingTabs` | `Attached` | 复用现有 `tabbar::landing()`，只是判定改为屏幕坐标 |
| `kDraggingWindow` | `Detached` | 拖影跟随光标 |
| `kDraggingUsingSystemDnD` | ≈ `Detached` | 同一形态；我们主动选它 |
| `kWaiting*` ×3 | 不需要 | 不进 move loop，就没有时序补丁 |
| `TabDraggingDestination` | `Target::{Same, New, Existing, None}` | 一个枚举，一个 `drop()` |

## 6. 能抄 / 抄不到

**能抄**

- 落点枚举与 `drop(dest)` 的单一提交路径；
- 15px 的磁吸阈值（上下对称）；
- 目标窗口按 z 序找、先提到前台再判条带；
- 源条带留占位；
- 拖影（非透明模式）的全部做法。

**抄不到**

- 被搬的对象是**已经 `SetParent` 进窗口 A 的 `CabinetWClass`**。分裂的真实动作是：
  在 B 里建 host → 把该子窗口 `SetParent` 到 B → 重算客户区 → 改 B 的 `is_absorbed` 表 → 让 A 忘掉它。
- 这一步没有任何开源参考，也正是历史僵尸窗口的来源。**手势是简单的部分，窗口搬家才是风险。**
